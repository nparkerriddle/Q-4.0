# Flex Q 4.0

Enhanced version of the Flex Q 3.0 recruiting pipeline spreadsheet, built as a **pure Excel workbook** (no app, no macros — formulas + Power Query only). This is a fresh, standalone effort, unrelated to the earlier `Flex Q/` React+Supabase project.

## Who it's for

YES Flex recruiters and onboarding staff. Non-technical end users, working in the workbook directly (desktop Excel, Microsoft 365).

## Files

- `Flex Q 3.0 (5).xlsx` — original file, untouched, kept as reference/backup.
- `Flex Q 4.1.xlsx` — the live working file (renamed by Nicholas from `Flex Q 4.0 - Rebuild.xlsx` around Round 31 — same file, new name, no other significance to the version bump).

## What's new vs 3.0

1. **PrepList** — added an `SSN #` column (col Q). PrepList is now the single autofill source (SSN, Name, Phone, Recruiter) keyed by Talent ID / Bold ID.
2. **START TEMPLATE tab** (first tab, bright green) — duplicate this for every new start date instead of copying an old dated tab. Type a Bold ID in column F; SSN/Name/Phone/Recruiter autofill via XLOOKUP against PrepList. New `Started` dropdown column (Started / No Show).
3. **Power Query `AllStartTabs`** — auto-discovers every tab duplicated from the template (via Excel Table name prefix `tbl_start`) and consolidates Bold ID / Recruiter / Started into a hidden table (`_StartedStatus` sheet, hidden). Refresh via Data → Refresh All whenever you want current numbers.
4. **Mini Orientation & PrepList** — new `Started Status` column, row highlights green when that Bold ID is marked Started anywhere on a start-date tab.
5. **Recruiter Scorecard tab** — per recruiter: placed on start tabs, started, no-show, still pending, start rate %. Static list of recruiter codes — add a row (copy formulas across) when a new recruiter is added.

## Key business rules / decisions

- **Bold ID = Talent ID** — same value, the join key across every tab.
- Tracking is scoped to **candidates placed on a start-date tab only** — a recruiter's "no start" count is people who made it onto a start tab but weren't marked Started, not earlier funnel drop-offs (PrepList/Mini Orientation no-shows aren't counted against recruiters here).
- Tracking starts fresh going forward from the rebuild date — the 100+ historical dated tabs (2023–2026, inconsistent column layouts) were **not** retrofitted into the tracker; they remain archive-only.
- New start-date tabs MUST be created by duplicating **START TEMPLATE** (Excel Table name prefix `tbl_start_...`) — a tab that isn't a Table with that prefix won't be picked up by the Power Query and won't feed the scorecard or status sync.
- No VBA/macros — the workbook stays a plain `.xlsx`, per explicit decision (macro security concerns across recruiter machines).
- SSN is now captured at the PrepList stage (added column) instead of first appearing at Mini Orientation — this is a workflow change recruiters need to know about.

## Round 33: tbl_Starts column reorder + SSN autofill fix (started this session, completed after pulling Round 32 from git)

**Major discovery, more consequential than anything else found this round: deleting and recreating a worksheet (even with the identical name) permanently breaks every external formula elsewhere in the workbook that referenced it — Excel converts them to `#REF!` and does not undo this even if a new sheet with the same name is created afterward.** This is fundamentally different from a sheet *rename* (which this project has repeatedly confirmed cascades correctly everywhere). First attempt at this reorder deleted-and-recreated `3.Starts` to rebuild it in the new column order — this appeared to work in-session, but Scorecard/Start Sheet For Flex were silently reduced to `#REF!` across the board. **Caught before ever touching the live file** (always testing on a disposable copy first paid off directly here). **Fixed by never deleting the worksheet itself** — instead: delete the ListObject (table) only, clear the sheet's used-range contents/CF/validation, write the new layout into the *same, still-alive* worksheet object, then rebuild the table fresh at the end. Since dependent formulas reference plain cell ranges (`'3.Starts'!$H$2:$H$2000`), not structured table references, they don't care about the table object's lifecycle — only the worksheet's. **Rule for any future full-rebuild of a sheet on this workbook: never delete the worksheet if anything anywhere else references it. Delete/recreate the Table object freely; never the sheet.**

**Second COM automation discovery this round, distinct from every prior one documented in this file**: PowerShell's dynamic call-site cache for a COM property **setter** (`.Value2 = x`) becomes unreliable — silently no-ops or throws a bogus `InvalidCastException` — specifically when the **value's .NET type alternates** across successive calls at the same call site in a tight loop (e.g. writing a string header, then a numeric date-serial, then more strings). Confirmed via roughly 15 isolated repro scripts before the real trigger was found; a bulk 2D-array `Range.Value2 = array` write showed a related but not fully isolated failure mode when the target range partially overlapped an existing wide Table's structure. **Fix: bypass PowerShell's dynamic dispatch entirely via reflection** — `$rangeObj.GetType().InvokeMember("Value2", [System.Reflection.BindingFlags]::SetProperty, $null, $rangeObj, @($val))` — 100% reliable across every retest, at the cost of being slower than plain per-cell `.Value2 =` (which remains fine for uniform-type writes, e.g. a loop that only ever writes formula strings).

**Third discovery: `Range.Replace()` silently fails (returns `True` but doesn't change anything) when the replacement text contains `@` characters** — surfaced while building a two-phase placeholder-based repoint (search old column ref → unique placeholder → final new column ref, needed to avoid old/new letters colliding mid-replacement when several columns swap positions at once). The exact mechanism wasn't fully traced, but it's reliably reproducible: identical calls succeed with `"TESTREPLACED"` as replacement text and fail with `"@@R1@@"`. **Fixed by using placeholders without `@`** (e.g. `ZZMOVER1ZZ`) — reliable across every retest. Worth remembering for any future find/replace automation on this workbook.

**Fourth issue, a real logic bug not a COM quirk**: after repointing Scorecard's Recruiter/Office column references to their new letters, the Started/No-Show `COUNTIFS` formulas started returning `#VALUE!`. Cause: `COUNTIFS` requires every range argument to be the same size — the Recruiter/Office side got updated to the new `$2000` bound, but the Started column (column A, letter unchanged by the reorder so never touched by the repoint step) was still carrying its old `$5029` bound from before. Mismatched range sizes across `COUNTIFS` arguments throw `#VALUE!` even when both ranges are otherwise valid. **Fixed by also updating every `'3.Starts'!$A$2:$A$<old bound>` reference to the new `$2000` bound**, even though column A's letter never moved — a reminder that a "column didn't move, no need to touch it" assumption can still miss a stale row-bound needing alignment with everything else that did move. Applied the same fix to a Start Sheet For Flex column (Flex AA) that had the identical stale-bound-only issue (harmless there since it wasn't paired in a multi-range formula, but corrected for consistency).

**Environment discovery, unrelated to Excel**: this automation repeatedly got killed mid-run by the OS's low-memory protection — traced to the *machine* running low on free RAM (several Edge browser windows, OneDrive sync, and other background apps consuming most of it), not anything about the automation's own (tiny) data footprint. Confirmed zombie Excel processes weren't the cause (cleaned up fully between attempts, still got killed). **Fixed by splitting the single monolithic rebuild script into four independent PowerShell invocations** (extract-and-clear → write-data-and-verify → formulas-and-table → dropdown/CF/filter), each opening Excel fresh, doing its piece, saving, and fully closing before the next starts — this keeps peak memory low at any given moment regardless of what else is competing for RAM on the machine. Data was staged between steps via a small JSON file on disk rather than kept in memory across script invocations. **If automation on this workbook gets killed for the same reason again, split further rather than trying to shrink the monolithic version.**
